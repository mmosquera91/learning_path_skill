<decisions>
## Implementation Decisions

### Migration Strategy
- **D-01:** Single migration v1→v2 — all missing columns, config keys, and constraints added in one migration step
- **D-02:** Migration backups stored in same directory as learning.db with version suffix (`learning.db.bak.v{current_version}`)
- **D-03:** Down-migration via `--down` flag on migrate_db.py — explicit, manual control (not auto-rollback on failure)

### Test Architecture
- **D-04:** Eval pipeline state transitions tested with mocked JSON input feeding directly into DB operations — no real LLM calls in tests
- **D-05:** Eval tests verify DB state transitions only (advance/repeat) — do not test Markdown prompt→SQL generation
- **D-06:** Test directory at project root (`tests/`), invoked via `python -m pytest tests/` per success criteria

### Claude's Discretion
- Response length limit for SEC-01 (user submission validation) — pick a reasonable limit based on common task response sizes
- DB file permissions enforcement scope (init_db.py creation only, or also enforce on existing DBs)
- Whether to also update README.md schema overview (requirement only specifies AGENTS.md for SCHEMA-03)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `scripts/init_db.py` — Idempotent DB setup with `CREATE TABLE IF NOT EXISTS` and `INSERT OR IGNORE`. Tests can verify this behavior directly.
- `scripts/migrate_db.py` — Version-based migration engine with ALTER TABLE support. Needs backup + down-migration added.
- `scripts/validate_urls.py` — Pure `classify_url()` function with clear tier classification logic. Highly testable with known-good/bad URL fixtures.

### Established Patterns
- Python scripts use stdlib only (sqlite3, json, subprocess, argparse, re, os, sys, pathlib, datetime)
- Error handling: `try/except` for specific exceptions, idempotent operations
- Type hints used in migrate_db.py (e.g., `conn: sqlite3.Connection`)
- Module docstrings, PEP 8 style
- CONSTANTS in UPPER_SNAKE_CASE

### Integration Points
- `scripts/init_db.py` is called at start of every cron job and `/tutor init` — changes must be backward-compatible
- `scripts/migrate_db.py` is run manually when schema changes needed — can extend interface
- SQL in Markdown files (SKILL.md, adapt.md) is generated by the LLM at runtime — parameterization must work within that constraint
- AGENTS.md schema docs are referenced by LLM when constructing SQL queries

</code_context>
